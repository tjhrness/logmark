1. Purpose and scope

1.1 What it does (plain English)

An AI governance lead needs subject-matter experts (SMEs) to manually
review a sample of AI-generated conversations each period, so the resulting
report can make a defensible statement about how often the AI gets things
wrong. Too small a sample and the statement is meaningless; too large and
the SMEs drown.
The tool answers, for one AI system and one period:

 1. How many conversations must be reviewed to state the issue rate to a
    chosen precision, and (optionally) to certify that the rate is below a
    threshold.

 2. How many SME hours that costs, including a second independent review
    of a subset (needed to measure reviewer consistency), and whether it fits
    the SME capacity available.

 3. If it doesn't fit, what the available hours buy — the best precision and the
    lowest certifiable threshold — with a slider to explore the trade-off.

 4. What the resulting report can and can't claim, in plain English, plus every
    formula and every intermediate number so an auditor can reproduce the
    headline with a calculator.

 5. After the review is done, what was actually achieved (observed rate,
    achieved margin, reviewer agreement), which feeds the next cycle's plan.

Every plan is saved as an immutable record; a generated CSV log gives a cycle-
over-cycle view across systems.


1.2 Who and where

Personal desktop tool for TJ's own use. Runs on his Windows machine, bound
to 127.0.0.1 only. No login, no network calls, no telemetry. It never sees
conversation content — only counts and rates.


1.3 In scope (v1)

Plan tab, Actuals tab, History tab, Method tab; the calculations in §4; warnings
in §5; statements in §6; persistence in §8; tests in §11.


1.4 Out of scope (parked for v2 — do not build, do not "helpfully"
add)

    Strata with Neyman allocation

    Uploading a conversation log to draw the actual random sample (needs a
    data-handling review before anything is uploaded)

    Generated PDF (e.g. reportlab); PyInstaller executable

    Cohen's kappa computed from double-review data; a confidence interval on
    the observed rate

    Trend view across cycles per system; SME cost in currency
    Deleting plans from the UI




2. Architecture

2.1 Shape

    One file, hitl_planner.py , containing: constants, calculation functions,
    validation, persistence, the Flask app, and the HTML/CSS/JS of the page
    as string templates. Nothing is loaded from the internet at any time (no
    CDN fonts, no CDN scripts); the tool MUST work fully offline.

    All maths in Python. The browser never computes a statistic. A small
    JavaScript layer sends the current inputs to POST /api/calc (debounced,
    ~150 ms after the last keystroke) and paints the returned results. No JS
    framework.

    Flask serves the page and a JSON API (§9). Python 3.11. Dependencies:
    Flask only; everything else from the standard library ( math , json , csv ,
    pathlib , datetime , webbrowser , os , re , argparse , socket ).

    Desktop only. No mobile layout.

    Look and feel: the same visual conventions as the Pareto and IMR tools
    (system font stack, light theme, card layout, inline CSS). Reuse their CSS
    where it exists.

2.3 Running it

 1. python hitl_planner.py — reads config.json (creating it with
    defaults if absent), runs the startup integrity check (§7.5), starts Flask on
    127.0.0.1:<port> , opens the default browser at http://127.0.0.1:
    <port>/ .

 2. Fixed port, default 5062 , stored in config.json . The build MUST check
    the Pareto and IMR scripts and pick a port that does not collide with either;
    record the chosen value in Appendix B on first commit.

 3. Single instance. Before binding, GET http://127.0.0.1:
    <port>/api/health is attempted. If it answers with this tool's name, the
    script opens the browser to the running instance and exits 0. If the port is
    held by something else, the script prints a one-line message naming the
    port and config.json , and exits 2.

 4. Quit button on every tab: POST /api/quit shuts the server down cleanly.
    Ctrl-C in the terminal also works.

 5. python hitl_planner.py --selftest runs the 11 answer-key cases
    (§11.1), prints PASS/FAIL per case, and exits 0/1 without starting the
    server.


2.4 Data stance

Bound to 127.0.0.1 only. No outbound HTTP. No analytics. Inputs are counts,
rates, hours and free-text notes; conversation content is never entered, stored
or requested.

3.3 Prefill and p_source

When the System field matches a saved system, the tool calls GET
/api/prefill?system=… and fills I1, I5–I7, I9–I15 from the most recent plan,
and I8 per the rule above. N stays blank. A banner reads: "Prefilled from 2026-
09 - HR Helpdesk Bot (v2) · p from actuals recorded 2026-10-03" (second
clause only when p came from actuals). Any field the user then edits is kept as
edited.

p_source is recorded with every plan: default (the 50 % preset, untouched),
manual (typed by the user), last_observed (from actuals), last_planned
(carried from the previous plan). Warning W2 (§5) keys on the presence of an
observed rate, not on p_source .

4.4 Trade-off panel (shown only when verdict is DOES NOT FIT)

 1. Capacity-max sample. n_max = the largest integer n in [0, min(N,
     floor(capacity × 60 / M + 1e-9))] such that fits(hours(n),
     capacity) where hours(n) = (n + min(n, max(F, ceil_safe(s ×
     n)))) × M / 60 . reviews(n) is non-decreasing in n, so a binary search
     is correct; a downward linear scan is acceptable. Both the panel and the
     headline MUST use the same hours() / fits() code.

 2. What n_max buys: E_at(n_max) (and its relative form in relative mode) via
     F9; T_at(n_max) via F10; DR , reviews and hours at n_max. If n_max = 0 ,
     the panel says capacity allows no reviews at all and shows no margin.

 3. What-if slider. Range ±2 % to ±15 % absolute (step 0.5 %) or ±5 % to ±50 %
     relative (step 1 %), initial position = the current margin. Moving it
    recomputes n, DR, hours and verdict live for display only, using the headline
    rule F5 (so with certify on, n cannot fall below n_assure , and the read-out
    says so) — the plan's inputs do not change. "Adopt this margin" writes the
    slider value into I7; the panel then disappears if the plan now fits.
    Confidence is not on the slider.


4.5 Sensitivity grid (always shown)

3 × 3 cells: margins {3 %, 5 %, 10 %} absolute or {10 %, 25 %, 50 %} relative
(matching the current mode) × confidence {90 %, 95 %, 99 %}. Each cell shows
n and SME hours computed with all other inputs as currently set, using the
headline rule F5 (so with certify on, a cell shows the larger of Cochran and
assurance for that confidence, with a small "A" mark when assurance binds).
Cells are coloured green (fits) or red (does not fit). The cell matching the
current confidence and margin is highlighted; if the current margin is a custom
value not in the grid, nothing is highlighted.

6. "What this sample can and can't say" — statement
templates

Always seven sentences, generated from the current numbers, shown on the
Plan tab and copied into plan_vN.json and report.html . {period} is the
display form ( Oct 2026 / 2026-W41 ).

Can say

   S1 (absolute): "The reported issue rate will be within ±{E} of the true rate for
   {system} in {period}, with {C} confidence."
   S1 (relative): "The reported issue rate will be within ±{r} of its own value (±
   {E} absolute at the expected rate of {p}), with {C} confidence."

   S2 (certify on, feasible): "If none of the {n} reviewed conversations shows
   the issue, you can state with {C} confidence that the true rate is below {T}."
   S2 (certify on, W7): "The 'below {T}' claim cannot be made at this
   population: it would need {n_assure} clean reviews and only {N}
   conversations exist."
   S2 (certify off): "This plan is not sized to certify that the rate is below a
   threshold; a 'below {T}' claim would need {n_assure} clean reviews."

   S3: "If the true rate were {T}, this sample has a {P} chance of containing at
   least one such conversation."

Can't say
    S4: "It says nothing about conversations outside {period}, or about systems
    other than {system}."

    S5: "The ±{E} applies to the overall rate only — not to any team, region or
    question type. Sub-groups need their own sample."

    S6: "These claims assume the {n} conversations are picked at random
    from all {N}. Hand-picking, or reviewing only flagged conversations, voids
    them."

    S7: "It measures how often SMEs find issues, not how severe they are or
    why they happen."




7. Screens

Four tabs in a top bar, plus a Quit button at the far right. A banner strip below
the tab bar shows global notices (integrity check failure, workspace not
writable). The page title is "HITL Sample Size Planner".


7.1 Plan tab

Left column — inputs, in four groups with a heading each:

 1. Identity: period type (segmented control), period picker, system (text with
    datalist auto-complete). Prefill banner appears under this group.

 2. Population and precision: N; confidence (dropdown); margin mode
    (segmented) with margin value (dropdown 3 / 5 / 10 in absolute mode, 10 /
    25 / 50 in relative mode, plus a "custom" entry that reveals a number field);
    expected issue rate p, with the one-line note "Leave at 50% if unknown —
    this gives the safest (largest) sample" and a small tag showing p_source .

 3. SME capacity: S, H (label reads "hours per SME this month/week" following
    the period type), M.

 4. Double review and certify: s, F, certify toggle, T.

Required-and-blank fields are outlined; while any input is invalid the outputs
column is greyed with the message "Complete the highlighted fields" and Save
is disabled.

Right column — outputs, top to bottom:

 1. Warning banners (§5), if any.

Appendix C — Glossary (plain English)

   Population (N) — every conversation the AI produced in the period.

   Sample (n) — the conversations the SMEs actually read.

   Margin of error (E) — how far the measured rate may be from the true rate.
   Absolute: ±5 percentage points. Relative: ±25 % of the rate itself.

   Confidence (C) — how often, over many repetitions, the true rate would fall
   inside the margin. 95 % is the convention.

   Expected issue rate (p) — the best guess before reviewing. 50 % is the
   worst case and gives the largest sample.

   Finite population correction — the adjustment that lets a smaller sample
   do the job when the population is small.

   Assurance / certify claim — "we reviewed n_assure conversations, found
   no issue, so the rate is below T". Holds only if none is found.

   Detection power — the chance a sample contains at least one issue if the
   true rate is T.

   Double review — a second SME independently reviews a subset so
   reviewer agreement can be measured.
Capacity — SMEs × net hours available this period.

Binding requirement — whichever of precision and certification demands
the larger sample.
